Jenkins + Ansible + Puppet + Terraform na SOF

Como criamos, configuramos e mantemos VMs e serviços de forma padronizada, auditável e repetível.

Visão de alto nível — Terraform (vCenter), Ansible (push) e Puppet (pull via pmng01).

Objetivo desta conversa

  • Entender o fluxo Terraform: Git (HCL) → Jenkins → Terragrunt → vCenter (criar/alterar VMs)
  • Entender o fluxo Ansible: Git → Jenkins → playbook → hosts
  • Entender o fluxo Puppet: Git → Jenkins → pmng01 → agentes nas VMs
  • Conhecer os blocos: pipeline, playbook, role / classe Puppet, terragrunt.hcl
  • Entender secrets: Jenkins Credentials + HashiCorp Vault (AppRole)
  • Ter um mapa rápido das áreas (Apache, WildFly, BDs, ELK…)

Não é um workshop hands-on — é o “mapa do território”.

Por que Jenkins + Ansible?

Padronizar

Mesma configuração em testes, homologação e produção, com inventários separados.

Repetir com segurança

Job parametrizado no Jenkins: quem, o quê, em quais hosts — com log e histórico.

IaC

Mudança de config vira código no GitLab (PR → main), não “ajuste manual na VM”.

Idempotência

Rodar de novo o playbook deve deixar o host no estado desejado, sem surpresas.

Fluxo em uma linha

GitLab (repo ansible) → Jenkins (pipeline) → ansible-playbook → SSH user ansible → VMs / serviços
  • GitLab guarda o código (playbooks, roles, inventários, Jenkinsfiles)
  • Jenkins é o “botão operacional”: parâmetros + execução + logs
  • Ansible aplica o estado desejado nos hosts do inventário

Estrutura do repositório

pipelines/

Jenkinsfiles por domínio (jppl_*). Parâmetros e chamada ao playbook.

playbooks/

Ponto de entrada Ansible: quais hosts, quais roles, ordem das tarefas.

roles/

Unidade reutilizável: instalar Apache, configurar pg_hba, sudoers, ELK…

inventories/

Quem são os hosts e grupos + group_vars / host_vars.

Conceitos: Pipeline → Playbook → Role

  • Pipeline (Jenkins): UI com parâmetros (HOSTS, INVENTORY, ENVIRONMENT…). Roda no agente e chama Ansible.
  • Playbook: “o que fazer nesta execução” — lista de roles e pré/pós tarefas.
  • Role: “como configurar um componente” — tasks, templates, handlers.

Exemplo mental

Job jppl_config_pg_hba
→ playbook config_pg_hba.yml
→ role pg_hba
→ template testes/sacpo.j2
→ arquivo no host + reload

Inventário e escopo

  • Inventário (*.ini): lista hosts e grupos (ex.: postgres_testes_siop)
  • HOSTS / --limit: restringe a execução a um grupo ou host
  • group_vars / host_vars: variáveis por grupo ou por máquina (sem misturar com a lógica da role)

Regra prática: o pipeline escolhe inventário + limit; a role não “adivinha” o ambiente — recebe parâmetros.

Dentro de uma role

tasks/

Passos (instalar pacote, copiar arquivo, reiniciar serviço).

templates/ (Jinja2)

Arquivos gerados com variáveis — ex.: pg_hba, httpd.conf, unit systemd.

files/

Arquivos estáticos ou scripts copiados como estão (ex.: script de install).

handlers/

Ações reativas: “só restart se o conf mudou”.

defaults/ / vars/

Valores padrão e variáveis da role.

scripts (shell)

Quando a lógica é longa demais para tasks — ainda orquestrados pelo Ansible.

Como o Jenkins executa (padrão SOF)

  • Credencial Jenkins ansible_pass_text → senha de sudo/become
  • Comando tipicamente: sudo -u ansible ansible-playbook …
  • Passa ANSIBLE_PASSWD / ansible_sudo_pass via -e
  • SSH nos alvos com usuário ansible + chave
  • Parâmetros do job viram -e e --limit

O agente Jenkins não “é root na VM alvo”: ele orquestra; quem muda o host é o Ansible como user ansible + become.

Secrets: dois cofres

Jenkins Credentials

  • Senhas e chaves usadas pelo job
  • Ex.: ansible_pass_text, chaves SSH
  • Injetadas no pipeline (credentials())
  • Não vão para o Git

HashiCorp Vault

  • Segredos de serviço / rotação
  • URL: vault.app.sof.intra
  • Paths tipo secrets/servicos/…
  • Jenkins acessa via AppRole

Nunca commitamos senhas em playbooks, inventários ou templates.

AppRole: Jenkins ↔ Vault

  • AppRole = identidade de máquina/aplicação no Vault (não é login de pessoa)
  • No Jenkins: credencial vault_approle_jenkins (role_id + secret_id)
  • Pipeline usa o plugin Vault (withVault) e lê só o path necessário
  • Exemplo: rotação de senha/chave do user ansible nos hosts
Job Jenkins → AppRole → Vault entrega secret → Ansible aplica no host

Em alguns jobs (ex. GitLab Runner), o token ainda pode ser passado como parâmetro — o padrão preferido para integração Jenkins é AppRole.

SCM: GitLab → Jenkins

  • O código mora no GitLab (repo ansible)
  • O job Jenkins é configurado com SCM Git apontando para esse repositório
  • Na prática: o workspace do job = checkout do branch (em geral main para produção)
  • O Jenkinsfile fica em pipelines/<área>/jppl_* e é referenciado no job (“Pipeline script from SCM”)
  • Fluxo de mudança: branch → Merge Request → main → próximo run do job já usa o código novo

Jenkins não inventa a config: ele executa o que está versionado no GitLab.

Ciclo de vida de uma mudança

1. Alterar role/template → 2. MR no GitLab → 3. Merge em main → 4. Rodar pipeline → 5. Conferir hosts
  • Prefira dry-run / ambiente de testes antes de produção
  • Escolha o limit certo (grupo ou host)
  • Leia o log do Jenkins — falha de SSH, sudo ou template aparece ali

Três camadas no ciclo de vida da VM

Terraform (provisionar)

Cria/altera a máquina no vCenter (CPU, RAM, disco, rede, tags) a partir do HCL.

Ansible (push)

Jenkins roda o playbook e empurra a config nos hosts do inventário naquela execução.

Puppet (pull)

Jenkins atualiza o servidor Puppet (pmng01); as VMs buscam a config no agent run.

IaC em todos: código no Git. Terraform fala com o vCenter; Ansible/Puppet falam com o SO/serviços dentro da VM.

Terraform: o que é (em uma frase)

O arquivo terragrunt.hcl descreve o estado desejado da VM no vSphere. O Jenkins aplica essa declaração no vCenter via Terragrunt/Terraform.

  • Repo infra/terraform: stacks em envs/<ambiente>/<site>/vms-*
  • HCL: nome, template, CPU, memória, IP, discos, tags — o “contrato” da VM
  • State no PostgreSQL: Terraform sabe o que já existe e o que precisa criar ou mudar
  • Não substitui Ansible/Puppet: depois da VM existir, a config do SO continua nos outros fluxos

Terraform: fluxo em uma linha

GitLab (repo terraform) → MR → main → Jenkins jppl_criaVM_* → terragrunt plan / apply → vCenter (API)
  • Usuário altera o terragrunt.hcl do grupo (ex.: envs/test/vsphere-516/vms-postgres)
  • Merge em main; job Jenkins faz checkout e usa credenciais do vCenter (+ Vault)
  • Plan mostra o que será criado/alterado; em prod há aprovação antes do apply
  • Apply clona o template e ajusta recursos no vCenter conforme o HCL

Parâmetros do job: Ambiente, Site (vsphere-516 / vsphere-k), Grupo (vms-*). O código da VM está no Git — não se “clica” a VM na mão no fluxo padrão.

Terraform: o que se muda no Git

terragrunt.hcl

Mapa vm = { … }: template, CPU/RAM, rede/IP, discos, tags, annotation.

modules/vsphere/vm/…

Lógica reutilizável (provider vsphere). Em geral não se edita por VM — só o stack em envs/.

pipelines/linux|windows

Jobs jppl_criaVM_*, tags, import — orquestram plan/apply no Jenkins.

Plan → Apply

Nova VM no HCL → create; mudar CPU/disco no HCL → update; remover do HCL → destroy (cuidado em prod).

Regra: edite o HCL → merge → rode o pipeline do stack certo. O Jenkins aplica no vCenter; o tfstate no Postgres registra o resultado.

Puppet: fluxo em uma linha

Gitea (repo puppet) → Jenkins jppl_SCM_* → Ansible sync → pmng01 → Puppet agent nas VMs
  • Usuário altera a classe no Git (sof/classes/<classe>/puppet/)
  • Pipeline Jenkins (pipelines/puppet/…/jppl_SCM_classes_puppet) publica no servidor
  • Playbook configura_puppet.yml copia o módulo para /opt/puppetlabs/puppet/modules/… no pmng01
  • Hosts com a classe aplicada recebem a config no próximo ciclo do puppet agent

Puppet: o que muda no Git

manifests/

Classe Puppet (init.pp) — o “o quê” configurar.

templates/ (.erb)

Arquivos gerados com parâmetros (ex.: httpd.conf.erb).

files/

Arquivos estáticos copiados para o host.

Pipeline + playbook

jppl_SCM_* + configura_puppet.yml + inventário puppet.ini (host pmng01).

Regra: edite no Git → rode o job da classe → aguarde o agent nas VMs. Não edite o módulo direto no pmng01.

O que um novato deve lembrar

  • Não edite config “só no servidor” se ela é gerida por role/classe/HCL — a próxima execução sobrescreve
  • Mude no Git, valide no Jenkins, aplique com limit / classe / stack conscientes
  • Terraform cria/altera a VM no vCenter; Ansible aplica na hora nos hosts; Puppet via pmng01 + agent
  • Secrets ficam no Jenkins/Vault — nunca no repositório
  • Em dúvida: rode primeiro em testes, leia o log (e o plan), peça revisão
